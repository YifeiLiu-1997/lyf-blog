2023.02 · Linux 服务

先用简单服务验证网络和文件访问路径

临时共享文件或验证局域网连通时，轻量 HTTP 文件服务适合快速确认链路。使用前要明确监听地址、端口、共享目录和访问范围；验证结束后关闭临时服务，避免把便捷调试入口长期暴露。

这类操作也提醒我，服务可用不等于服务已安全部署。命令、当前工作目录和访问地址都应一起记录，减少换机器后因上下文不同而产生的误判。

项目周期 · 2023.06–2023.12

兼容性测试先把“兼容”变成可判断的问题

软件包兼容性分析首先要说清被测对象、目标环境和依赖关系。把环境信息与扫描对象一起纳入分析，才能解释某个结论适用于什么条件，避免把一次测试结果泛化成所有机器都适用。

在平台设计中，问题描述、输入信息、分析过程和结论应尽量分开表达。后续出现新的系统环境或软件包时，才有机会扩展判断逻辑，而不是在页面上不断堆叠特例。

项目周期 · 2023.06–2023.12

Django 与 React 分工，关键是稳定的接口契约

前后端分离不是把页面和服务拆成两个仓库就结束。后端负责数据与业务规则，前端呈现状态与用户操作；两边通过明确的请求、响应和错误语义协作，才能减少各自猜测对方行为的情况。

接口字段、必填条件、异常返回和加载状态应能从实现或文档中查到。改动接口时同步检查调用端，可以把问题拦在集成阶段，而不是等用户操作到某个边界才暴露。

技术基础：Django 官方入门文档 · React 官方学习文档

项目周期 · 2023.06–2023.12

扫描结果要可解释、可定位、可重复

依赖扫描的价值不只在于给出一条结论，还在于说明分析针对哪个软件包、读取了哪些依赖信息，以及结果如何对应到被测环境。将原始输入和分析结果保持关联，能让后续复查不必从头猜测。

处理文件时要考虑格式差异、缺失项和解析失败。把失败单独呈现并保留原因，比将异常吞掉后生成一个看似完整的结果更可靠，也方便逐步扩充对新输入的支持。

项目周期 · 2023.06–2023.12

MySQL 数据结构跟着分析对象和查询路径设计

为兼容性分析存储数据时，先梳理核心对象之间的关系，再决定哪些信息需要单独保存、哪些适合通过关联查询得到。字段含义与状态变化定义清楚，页面展示和后续筛选才有一致的数据基础。

数据库问题应结合真实查询和数据样例验证，而不是只看表结构是否“看起来合理”。随着数据量与查询方式变化，再按实际访问路径评估索引和查询成本，避免过早复杂化。
