Ceph HEALTH_WARN：先观察，再定位

健康告警是排查入口，不是诊断结论。建立只读证据链，区分集群映射、OSD、PG 和容量问题，再决定是否需要变更。

整理于 2026-09-26约 6 分钟命令仅用于只读检查

遇到 HEALTH_WARN 时，第一反应不应该是清告警或重启全部服务，而是先回答：影响范围是什么、从什么时候开始、哪些服务参与了状态变化、最近是否有扩容或维护操作？同一个告警状态可能由完全不同的原因触发。

先收集一组只读快照

以下命令用于查看当前状态。执行前仍要确认连接的是目标集群，避免把生产和实验环境混淆。

ceph -s
ceph health detail
ceph osd tree
ceph pg stat
ceph df
ceph orch ps

把输出与时间、集群版本、最近变更一起保存。若问题正在变化，可以间隔一段时间重新采集同一组信息，比较变化趋势，不要只凭一个瞬时状态推断根因。

按故障域逐层缩小范围

1. MON 与集群映射

先看 Monitor quorum 是否稳定、集群时钟是否正常、节点间连接是否可达。控制面不稳定时，后续看到的服务状态可能不完整；此时应优先确认网络、时间和 Monitor 服务，而不是直接操作 OSD。

2. OSD 与主机

通过 OSD 树确认哪些守护进程是 down 或 out，再把它们对应到主机、设备和近期日志。一个主机故障会同时影响该主机上的多个 OSD；如果故障域配置不合理，影响面可能超过直觉预期。

3. PG 状态与恢复

查看 PG 是否 degraded、undersized、stale 或处于恢复队列。恢复通常需要时间和资源，应该结合 OSD 可用性、容量与业务负载观察。不要把“等待恢复完成”误认为某个命令可以安全地强制清除。

4. 容量和空间水位

结合 pool / OSD 使用率、full ratio 告警和新增数据速度判断是否接近容量边界。空间告警既可能需要扩容，也可能来自数据分布倾斜或恢复暂时占用；先读清具体 health detail，再制定容量方案。

把“证据—原因—动作”写下来

  1. 记录原始告警与命令输出，不要先清理现场。
  2. 将告警映射到 MON、主机 / OSD、PG、容量或客户端链路。
  3. 核对最近的发布、网络、磁盘或配置变更，并用日志验证假设。
  4. 提出最小范围、可回滚的处置计划；明确数据风险、维护窗口和负责人。
  5. 变更后重新采集相同状态，确认健康和数据冗余恢复，再记录复盘结论。
避免把 ceph osd out、删除 OSD、修改 CRUSH 或切换集群 flag 当成通用修复步骤。这些都是有状态变更，必须先理解具体故障、影响范围和恢复方案，并按所用 Ceph release 的官方操作指南执行。
